# Design — Keisar Club Platform (v1)

> **Status**: Living document. v1 scope only. v2 lives in `design-v2.md`. Non-code tasks in `non-code-tasks.md`. Proposal will be drafted once v1 scope freezes.

---

## Context

`keisar.club` is currently a single-tenant freelance portfolio (React + Vite + Supabase) presenting Amitay's personal work as a developer. The site is a static showcase: portfolio items rendered into infinite-spiral carousels, with no auth, no users, and no transactions.

The site is being repositioned as the public face of **Keisar Club**, a development agency that:

- Signs all client contracts directly (Amitay as the prime contractor / agency).
- Engages developers as **per-project freelancers** (not employees).
- Manages all client communication, project scoping, and dev assignment in-house (initially Amitay, later dedicated PMs).
- Pays developers a per-project fee from revenue collected from clients.

The site's role in the new model is twofold:

1. **Public showroom** — case studies of projects shipped under Keisar Club, with attribution to the developers who built them (when both client and dev opt in).
2. **Private intake pipe** — a place where invited developers self-onboard, fill out their profile, and become available to be assigned to projects.

The site is **not** a marketplace. It does not host messaging, payments, applications, or matching algorithms in v1. Those are out of scope or deferred to v2.

Domain stays at `keisar.club`. No rebrand of the URL.

---

## Goals / Non-Goals

### Goals

- Reposition the site from "Amitay's portfolio" to "Keisar Club agency showroom" while preserving the existing visual language (spirals, shaders, glass aesthetic).
- Allow Amitay to invite a developer by email and have them self-onboard a profile in one sitting.
- Allow Amitay to publish projects with the new fields needed for an agency (company, duration, status, attributed developers, visibility flags).
- Show three project spirals on the home page: **Upcoming**, **Ongoing**, **Finished**.
- Capture (in the data model) future-needed fields like `assignedManager` even though Amitay is the only manager today.
- Respect both client-side and dev-side opt-in for public attribution.
- Stay on Supabase — reuse Auth, Storage, Postgres, and RLS rather than rebuilding them.

### Non-Goals (v1)

- No client login or self-serve project posting (Amitay creates all projects in the admin in v1).
- No "apply to project" button for devs.
- No dev-facing project dashboard ("My projects" tab) — deferred to v2.
- No public dev directory page — deferred to v2.
- No on-platform messaging.
- No on-platform payments.
- No automated GitHub-review agent.
- No re-verification workflow (changes go live; flagged manually if needed).
- No Apple Sign-In.
- No migration off Supabase.
- No vetting workflow UI — interviews happen on Zoom; status is a flag in the DB.

## Decisions

### Decision 1: Login providers — Google + GitHub only (no Apple)

**Choice:** Enable Google OAuth and GitHub OAuth via Supabase Auth. No password login. No Apple Sign-In.

**Why:**
- GitHub login gives a verified handle that can later feed an automated capability review (v2). It is the strongest signal of "is this person a real developer."
- Google login keeps the door open for clients (and for devs who, for legitimate reasons, do not have public GitHub activity — e.g. five years at a company that bans public repos).
- Apple Sign-In adds meaningful complexity on web (domain verification, JWT key rotation, popup quirks) for a population that overlaps almost entirely with Google. Skipped.
- No passwords means no credential reset flows, no credential stuffing surface, no "forgot password" UI.

**Implementation note:** Both providers are configured in the Supabase project dashboard. The app uses `supabase.auth.signInWithOAuth({ provider: 'google' | 'github' })`. After OAuth callback, the app reads `auth.users.id` and joins it to a `profiles` row.

**GitHub identity quirk:** GitHub OAuth surfaces `user_metadata.user_name` (handle) and sometimes `email`, but real legal name is not always present. The onboarding form re-asks for legal name explicitly.

### Decision 2: Invite-only registration, single-use tokens tied to email

**Choice:** No public sign-up. To register, a developer must follow a unique invite link generated by Amitay in the admin. The invite token is bound to a specific email address and is single-use.

**Why:**
- Prevents spam signups and identity-flipping at the front door.
- Forces the curation that defines Keisar Club ("only the best").
- Lets Amitay onboard a dev he meets in real life by sending one link instead of doing manual data entry.

**Token mechanics:**

| Property | Value |
|---|---|
| Length | 32-byte URL-safe random |
| Storage | Supabase table `dev_invites(token_hash, email, created_at, expires_at, used_at, invited_by)` |
| Storage of token | SHA-256 hash; raw token is shown to Amitay once at creation, sent to dev in URL |
| Expiry | 30 days from creation |
| Single-use | `used_at` is set on first successful registration |
| Email binding | The OAuth provider must return an email matching the invite's email, OR the onboarding form requires the dev to confirm and the email matches via case-insensitive compare. If GitHub login returns no email or a non-matching email, the dev can verify by clicking a magic link sent to the invite email. |

**Edge case:** if a dev's GitHub account has a different verified email than the one Amitay invited, the registration is blocked with a clear error ("This invite is for `x@y.com`. Please contact us to update."). Amitay can re-issue the invite in admin.

### Decision 3: Project schema upgrade — additive, not destructive

The existing `PortfolioItem` shape (see `src/types/portfolio.ts`) is preserved. New fields are added to support the agency model.

**New fields on the `projects` table:**

| Field | Type | Notes |
|---|---|---|
| `companyName` | `text \| null` | Client company displayed publicly when `clientVisibility = 'public'`. |
| `duration` | `text \| null` | Free-text ("3 months", "Q2 2026"). Not a date range — durations are messy. |
| `status` | `enum('upcoming','ongoing','finished')` | Drives which spiral the project appears in. Replaces the old optional `status` enum. |
| `developers` | `uuid[]` (FK to `profiles.id`) | Devs who worked on this project. Order is meaningful (lead first). |
| `assignedManager` | `uuid` (FK to `profiles.id`) | Always Amitay's profile id today. Future PMs slot in here without migration. |
| `clientVisibility` | `enum('public','logo_only','hidden')` | What the public site shows about the client. |
| `devAttribution` | `enum('named','anonymized','hidden')` | What the public site shows about the assigned devs. |
| `startedAt` | `date \| null` | When work actually started (for ordering Ongoing). |
| `finishedAt` | `date \| null` | When work shipped (for ordering Finished). |

**Backwards compatibility:**
- All existing portfolio items are migrated with `status='finished'`, `developers=[amitay_profile_id]`, `assignedManager=amitay_profile_id`, `clientVisibility='hidden'`, `devAttribution='named'`.
- Existing rendering of the gallery section continues to work — it queries `status='finished'` by default until the new spirals replace it.

### Decision 4: Three spirals on the home page

**Choice:** Replace (or extend) the current single project spiral with three labeled spirals: **Upcoming**, **Ongoing**, **Finished** — each driven by `projects.status`.

**Why:**
- Reuses the most distinctive visual element of the site.
- Naturally communicates the agency's pipeline ("we have work coming, we ship work, we have a track record") to visitors.
- Gives invited devs (and future applicants) a way to see what's available.

**Order of appearance on the page:** Finished → Ongoing → Upcoming, top to bottom. Reasoning: visitors land on the strongest signal first (proof of completed work). Devs scrolling for opportunities will reach Upcoming naturally as they descend.

**Empty-state policy:** if Upcoming has zero items at launch, the spiral is hidden (not shown empty). If Ongoing has zero items, hidden. Finished must have at least one item to launch.

**Direction of spin:** Finished left, Ongoing right, Upcoming left. (Visual variety; no semantic meaning.)

### Decision 5: Visibility — controlled by Amitay in v1, by users in v2

**Choice:** In v1, `clientVisibility` and `devAttribution` are set by Amitay in the admin UI when creating/editing a project. They reflect what was negotiated with the client and the dev offline.

In v2, the dev gets controls in their own dashboard to hide their attribution on specific projects, and the client (once client login exists) can adjust client-side visibility on their own projects.

**Why split:**
- Day 1, there are no client accounts and very few dev accounts — Amitay knows what each side wants.
- Building user-facing controls in v1 is wasted work until there are users to use them.
- The data model already supports per-side opt-in, so v2 is purely UI work on top.

**Default values when creating a new project in admin:**
- `clientVisibility = 'logo_only'` (most common case).
- `devAttribution = 'named'` (devs almost always want credit).

### Decision 6: Soft verification only — no automated re-verification in v1

**Choice:** Profile changes go live immediately. No "pending" state. Amitay can manually flag/suspend a profile in the admin if something looks off.

The only verification check applied at registration is **name-flip detection**: when a dev edits their `fullName` after initial save, the previous value is recorded in a `profile_audit` table. If a profile flips its name more than once, the admin sees a warning badge.

**Why:**
- v1 has tens of devs, all hand-invited. Real-time fraud is not the threat model.
- A "pending review" workflow creates a queue Amitay must process — operational debt before there's enough volume to justify it.
- Recording history is cheap and lets v2 build a real workflow on top.

### Decision 7: Stay on Supabase — defer Cloudflare D1/R2

**Choice:** No infrastructure migration. Keep using Supabase for Postgres, Auth, Storage, and Realtime.

**Why:**
- Supabase already provides OAuth, RLS (which exactly matches the "devs see their stuff, clients see theirs" pattern needed in v2), file storage with policies, and an admin UI.
- A migration to D1/R2 means re-implementing auth, storage policies, and image upload handling — weeks of work that delivers zero user-visible value.
- Re-evaluate only when there is a measured scaling problem (DB CPU, storage cost, latency).

### Decision 8: Admin UI — first-class, not deferred

**Choice:** Build a private `/admin` route accessible only to profiles with `role = 'admin'`. Admin can:

- Generate dev invite links (paste an email, get a copyable URL).
- See all profiles with their current verification status, GitHub handle, and last activity.
- Flag/suspend a profile.
- Create, edit, and delete projects (full CRUD).
- Set `developers`, `assignedManager`, `clientVisibility`, `devAttribution` per project.

**Why first-class:**
- Without this, Amitay edits Supabase rows by hand for the foreseeable future. That is the path to data corruption.
- The admin UI is also the prototype of the v2 "PM dashboard" — the same screens, with `role = 'manager'`, become tomorrow's PM tool.

## Data model — full v1 schema

```
profiles
├── id              uuid PK (= auth.users.id)
├── role            enum('admin','manager','dev','client')   -- v1 uses admin + dev
├── github_handle   text       -- pulled from GitHub OAuth, editable
├── full_name       text       -- legal name, re-asked on onboarding
├── display_name    text       -- shown publicly, defaults to full_name
├── avatar_url      text       -- defaults to OAuth provider avatar
├── bio             text
├── resume_url      text       -- optional R2/Supabase Storage URL
├── links           jsonb      -- { github, linkedin, website, twitter, ... }
├── status          enum('active','suspended')  default 'active'
├── invited_by      uuid FK -> profiles.id (nullable)
├── created_at      timestamptz default now()
└── updated_at      timestamptz default now()

profile_audit
├── id              bigserial PK
├── profile_id      uuid FK -> profiles.id
├── field           text       -- 'full_name', 'avatar_url', etc.
├── old_value       text
├── new_value       text
└── changed_at      timestamptz default now()

dev_invites
├── id              uuid PK
├── token_hash      text       -- SHA-256 of the token
├── email           citext     -- target email, case-insensitive
├── invited_by      uuid FK -> profiles.id
├── created_at      timestamptz default now()
├── expires_at      timestamptz default (now() + interval '30 days')
└── used_at         timestamptz nullable
                                -- index: (token_hash) unique, (email) where used_at is null

projects                       -- supersedes the current portfolio_items shape
├── id                  uuid PK
├── sku                 text unique
├── lang                enum('en','he')
├── title               text
├── image               text
├── image_pack          text[]
├── featured            boolean
├── description         text
├── long_description    text
├── technologies        text[]
├── settings            jsonb
├── project_type        text
├── additional_info     jsonb
├── problem             text
├── what_i_built        text
├── how_it_works        text
├── result              text
├── priority            int
├── completion_date     date
├── live_site           jsonb
├── github              jsonb
├── publish             boolean
├── -- new in v1 --
├── company_name        text
├── duration            text
├── status              enum('upcoming','ongoing','finished')
├── developers          uuid[]                 -- ordered, lead first
├── assigned_manager    uuid FK -> profiles.id
├── client_visibility   enum('public','logo_only','hidden')
├── dev_attribution     enum('named','anonymized','hidden')
├── started_at          date
├── finished_at         date
├── created_at          timestamptz default now()
└── updated_at          timestamptz default now()
```

### RLS policies (Supabase Postgres Row-Level Security)

| Table | Who can read | Who can write |
|---|---|---|
| `profiles` | Anyone (public columns only via a view); self for full row | Self for own row; admin for any row |
| `profile_audit` | Self; admin | Inserted by trigger only |
| `dev_invites` | Admin only | Admin only |
| `projects` | Anyone for `publish=true`; admin for all | Admin only |

**Public profiles view:** `profiles_public` exposes only `id, display_name, avatar_url, github_handle, bio, links` for `status='active'` profiles. The full `profiles` table is never readable by anonymous clients.

## Routes — v1 site map

| Route | Access | Purpose |
|---|---|---|
| `/` | public | Hero + 3 spirals (Finished, Ongoing, Upcoming) + existing sections |
| `/projects/:sku` | public | Case study; renders attributed devs per `devAttribution` |
| `/login` | public | "Continue with Google" / "Continue with GitHub" |
| `/onboard?token=...` | invite-token-gated | Self-serve dev registration form |
| `/me` | logged-in dev | Edit profile (name, avatar, bio, links, resume) |
| `/admin` | role=admin | Profiles list, invite generator, project CRUD |
| `/admin/projects/:id` | role=admin | Edit a project |
| `/legal/terms` | public | Terms of service |
| `/legal/privacy` | public | Privacy policy |

**Routes deliberately NOT in v1:** `/devs/:handle` (public dev page), `/me/projects` (dev's project dashboard), `/clients/*`, `/projects/:sku/apply`.

## v1 build checklist (high-level)

1. **Supabase setup**
   - Enable Google + GitHub OAuth providers in Supabase dashboard.
   - Create `profiles`, `profile_audit`, `dev_invites`, `projects` tables.
   - Migrate existing `portfolio_items` → `projects` with defaults.
   - Write `profiles_public` view.
   - Write RLS policies and audit trigger.

2. **Auth integration**
   - `supabase.auth.signInWithOAuth` for both providers.
   - On callback, upsert into `profiles` (do not overwrite user-edited fields).
   - Auth context / hook for the React app.

3. **Onboarding flow**
   - `/onboard?token=...` page reads token, validates against `dev_invites`, shows registration form.
   - Form fields: legal name (required), display name (defaults to legal), avatar (uses OAuth avatar or upload), bio, resume (optional file upload to Supabase Storage), links.
   - On submit, mark invite `used_at`, create profile.

4. **Dev profile editor**
   - `/me` page: same fields, editable, with audit trigger recording each change.

5. **Admin**
   - `/admin` profiles list (search, filter by status, suspend toggle).
   - `/admin/invites` create form (email → generates copyable URL).
   - `/admin/projects` table with status filter.
   - `/admin/projects/:id` editor with all new fields, dev multi-select, manager picker.

6. **Public site upgrades**
   - Three spirals on home page driven by `status`.
   - Project case study renders `companyName`, `duration`, attributed devs (per `devAttribution` and `clientVisibility`).
   - Empty-state handling for Upcoming/Ongoing.

7. **Legal pages**
   - Static `/legal/terms` and `/legal/privacy` (content provided by lawyer — see `non-code-tasks.md`).

8. **Pre-launch data work**
   - Amitay creates his own admin profile.
   - Existing finished projects backfilled with `developers=[amitay_id]`.
   - 1–3 ongoing projects entered.

3. Should the avatar uploaded by a dev replace the OAuth avatar permanently, or sync from OAuth on each login? (Recommendation: replace permanently once user uploads; never auto-overwrite.)
4. What's the launch list of Ongoing projects? Need at least the SKUs and assigned devs to seed the spiral.
